# Мини-ТЗ: Система учёта обращений (venue analytics) для Basen.uz

> Как использовать: этот документ можно целиком вставить как промпт в Claude Code / Cursor
> вместе с доступом к репозиторию проекта. Реализовывать по разделам, начиная с раздела 3.

---

## 1. Цель

Считать конверсионные действия посетителей по каждому объекту каталога (бассейну) и показывать
статистику в двух видах:

1. **Себе** — сводная таблица по всем объектам, чтобы понимать, кому продавать платное размещение.
2. **Владельцу объекта** — красивая страница по закрытой ссылке, которую можно открыть
   на телефоне при личной встрече.

Данные храним бессрочно (статистика лета понадобится следующей весной).
Яндекс.Метрика / GA4 остаются как есть — своя аналитика их дополняет, а не заменяет.

## 2. Контекст и стек

- Проект: Nuxt 3 + Vue 3, SSR. Отдельного бэкенда нет — **используем Nitro server routes
  (`server/api/`)**, отдельный сервер не поднимать.
- База данных: **Supabase (Postgres, бесплатный тариф)**. Ключи — только в env-переменных,
  обращение к Supabase только из server routes (service role key на клиент не попадает).
  - Альтернатива, если хостинг позволяет файловую систему: SQLite через better-sqlite3.
    По умолчанию — Supabase.
- Трекинг не должен влиять на скорость сайта: никаких тяжёлых библиотек, никаких блокирующих
  запросов при рендере.

## 3. События, которые считаем

| event_type | Когда срабатывает |
|---|---|
| `view` | Открытие страницы карточки бассейна (1 раз за сессию на объект) |
| `call_click` | Клик по номеру телефона (ссылка `tel:`) |
| `telegram_click` | Клик по ссылке на Telegram объекта |
| `route_click` | Клик «построить маршрут» / переход в карты |
| `website_click` | Клик по сайту объекта (если поле есть) |

К каждому событию сохраняем:

- `venue_id` — идентификатор объекта (slug или id из каталога)
- `event_type` — из белого списка выше
- `source` — откуда пришёл посетитель: `yandex` / `google` / `instagram` / `telegram` /
  `direct` / `other`. Определять по `document.referrer` и utm-меткам (utm_source приоритетнее)
- `device` — `mobile` / `desktop` (по user-agent на сервере)
- `fingerprint` — hash(IP + user-agent), считается на сервере. IP в открытом виде НЕ хранить
- `created_at` — timestamp

## 4. Схема данных

```sql
create table venue_events (
  id bigserial primary key,
  venue_id text not null,
  event_type text not null,
  source text not null default 'direct',
  device text,
  fingerprint text not null,
  created_at timestamptz not null default now()
);

create index venue_events_main_idx
  on venue_events (venue_id, event_type, created_at);
create index venue_events_dedup_idx
  on venue_events (fingerprint, venue_id, event_type, created_at);

-- Доступ владельцев к своей статистике
create table stats_tokens (
  token text primary key,          -- случайная строка 32+ символа
  venue_id text not null,
  label text,                      -- «Владелец, Азиз-ака» — для себя
  created_at timestamptz not null default now(),
  revoked boolean not null default false
);
```

## 5. API (Nitro server routes)

### POST `/api/track`

Приём события с клиента.

- Тело: `{ venueId, eventType, source }`
- Валидация: `eventType` строго из белого списка; `venueId` существует в каталоге
  (проверка по списку объектов). Иначе — 204 без записи (не подсказывать ботам, что не так).
- **Дедупликация:** одинаковая тройка (fingerprint, venue_id, event_type) пишется не чаще
  1 раза в час. Реализация: перед вставкой — select последнего события этой тройки за час.
- Ответ всегда `204 No Content`, максимально быстрый.
- Фильтр ботов: отбрасывать известные краулеры по user-agent (Googlebot, YandexBot,
  bingbot, AhrefsBot и т.п.).

### GET `/api/stats/:venueId?token=...&period=30`

Агрегаты для страницы владельца.

- Авторизация: токен из `stats_tokens` должен соответствовать `venueId` и не быть отозван,
  иначе 403.
- `period`: 7 / 30 / 90 / 365 дней (по умолчанию 30).
- Ответ:

```json
{
  "totals": { "view": 1240, "call_click": 87, "telegram_click": 45, "route_click": 61 },
  "series": [ { "week": "2026-07-06", "view": 320, "call_click": 21 }, ... ],
  "sources": { "yandex": 410, "google": 520, "instagram": 190, "direct": 120 }
}
```

### GET `/api/admin/stats?period=90`

Сводка по всем объектам для себя. Авторизация: секрет в заголовке или простая admin-сессия
(на усмотрение, но не публично). Ответ: массив объектов с суммами по типам событий,
отсортированный по `call_click + telegram_click` по убыванию.

## 6. Фронтенд

### Composable `useTrack()`

```ts
// composables/useTrack.ts
export function useTrack() {
  function track(venueId: string, eventType: string) {
    if (import.meta.dev) return            // не трекать в разработке
    const payload = JSON.stringify({
      venueId,
      eventType,
      source: detectSource(),              // referrer + utm из URL/сессии
    })
    if (navigator.sendBeacon) {
      navigator.sendBeacon('/api/track', new Blob([payload], { type: 'application/json' }))
    } else {
      fetch('/api/track', { method: 'POST', body: payload, keepalive: true })
    }
  }
  return { track }
}
```

Важно: именно `sendBeacon` / `keepalive` — клик по `tel:` мгновенно уводит браузер
в звонилку, обычный fetch может не успеть отправиться.

### Интеграция в карточку объекта

- `view` — в `onMounted` страницы карточки; дедуп на клиенте через `sessionStorage`
  (ключ `viewed:<venueId>`), чтобы не слать при каждом возврате назад.
- Остальные события — обработчики на соответствующих кнопках/ссылках. Клик не задерживать:
  сначала beacon, переход по ссылке идёт своим чередом.
- utm-метки при первом заходе сохранять в `sessionStorage`, чтобы source не терялся
  при переходах внутри сайта.
- Дубль в GA4 одной строкой: `gtag('event', eventType, { venue_id: venueId })` — как резерв
  и для сверки.

## 7. Страница статистики владельца — `/stats/[venueId]`

Доступ по `?token=...`. Это инструмент продаж — она должна выглядеть убедительно
и открываться с телефона.

- Шапка: название и фото объекта, период (переключатель 7 / 30 / 90 дней / сезон).
- 4 KPI-карточки: просмотры, звонки, переходы в Telegram, маршруты — крупные числа.
- График по неделям (bar или line) — просмотры и обращения.
- Разбивка по источникам (Яндекс / Google / Instagram / прямые) — донат или горизонтальные бары.
- Внизу ненавязчивый блок: «Хотите больше обращений? Премиум-размещение» + кнопка в Telegram.
- Языки: RU (по умолчанию) и UZ. Мобильная вёрстка обязательна.
- SSR не нужен, `robots: noindex`.

## 8. Админ-сводка — `/admin/stats`

Минимальная таблица: объект, просмотры, звонки, Telegram, маршруты, сумма обращений,
сортировка по столбцам, фильтр по категории и региону. Цель — за 30 секунд увидеть
топ объектов, которым стоит предлагать платное размещение.

## 9. Сопутствующая задача: единое число объектов

Сейчас на сайте одновременно «93+», «50+» и «более 100 бассейнов». Завести один источник
правды — количество опубликованных объектов из данных каталога — и выводить его во всех
местах (hero, футер, about, meta description) из этого значения.

## 10. Не входит в эту итерацию (v2)

- Realtime-обновление статистики
- Экспорт в CSV / PDF-отчёты владельцам
- Email/Telegram-дайджесты
- A/B-тесты карточек

## 11. Критерии приёмки

1. Клик «позвонить» с мобильного фиксируется в БД, даже если браузер мгновенно ушёл
   в звонилку (проверить на реальном телефоне, Android и iOS).
2. Повторные клики одного посетителя по одной кнопке в течение часа НЕ увеличивают счётчик.
3. `view` считается один раз за сессию на объект.
4. `/stats/<id>?token=<валидный>` открывается без логина; с чужим или отозванным токеном — 403.
5. Страница владельца показывает данные за 90 дней и открывается быстро (< 1 сек на 4G).
6. События ботов (Googlebot и т.п.) не попадают в статистику.
7. Расхождение сумм со счётчиками GA4 за неделю — в пределах ~10%.
8. Везде на сайте отображается одно и то же число объектов, взятое из данных.
9. Service role key Supabase отсутствует в клиентском бандле (проверить в собранном JS).
